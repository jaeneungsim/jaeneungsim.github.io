One MCP server for the whole team

The team docs search MCP server used to run on each developer's computer. Now it runs once, as a remote server on AWS Lambda. Developers approve the repository's .mcp.json once and sign in with their own account. A fix reaches everyone with one deploy, and a rollback only moves an alias.

The problem

AI agents reach company systems such as internal docs, tickets and databases through MCP servers. The team docs search from my previous project was a local MCP server that ran on each developer's computer. That is the easiest way to start when one person uses it. Once a team shares it, it gets harder to manage.

  • Everyone updates on their own. A fix has to be installed on every computer, so people easily end up on different versions. It is also hard to see in one place who is on which version.
  • Credentials sit on developers' computers. A local server that calls a company system needs credentials on each computer. The previous project narrowed them to an AWS role that can only call the search, but everyone still needed AWS settings and a sign-in.
  • Usage records are scattered. To see who uses which tool, you have to collect records from each computer.

The MCP documentation (Local Server Security) recommends the remote version of a server when there is one. A remote server runs no code on the developer's computer, uses the spec's sign-in flow instead of tokens in local config files, and is fixed in one place. For organizations, it recommends central distribution, an inventory of who uses what at which version, and audit logs. GitHub (September 2025), Atlassian (February 2026) and AWS (May 2026) also offer the MCP servers for their own services as remote servers, generally available.

So I moved the team docs search to a remote MCP server. The search itself is the one from the previous project; a remote server now sits in front of it. Because both use the same search, the local and the remote server can be compared under the same conditions.

Principles

  1. One server. A fix reaches everyone with one deploy, and a rollback happens in one place too.
  2. Follow the spec. Sign-in follows the MCP authorization spec (OAuth), and the client is Claude Code as it is. There is no custom sign-in method and no extension.
  3. Check that each token was issued for this server. The signature, expiry, issuing app, audience (aud) and scope are all checked. A token is never passed on to anything else.
  4. Keep company credentials on the server side. A developer's computer holds only the token for this server.
  5. Log in one place, and only what is needed. Who called which tool, when, on which version. Never tokens or question text.
  6. No cost while idle. Nothing with a fixed monthly cost.

Architecture

1. Sign-in

  • When a developer opens Claude Code in the repository for the first time, Claude Code asks once whether to use the team-docs-remote server from the repository's .mcp.json.
  • The first tool call gets a 401 from the server. Claude Code reads the server's protected resource metadata (RFC 9728) to find the authorization server, Amazon Cognito, and opens the sign-in page in the browser. It sends PKCE and resource (the server URL) with the request.
  • Cognito has no endpoint for automatic client registration. So a public client for Claude Code (no secret) is registered in advance, and its client ID and callback port go in .mcp.json. The MCP spec accepts pre-registration as a standard way to get a client ID. Cognito matches callback URLs exactly and takes no port ranges, so the port is fixed.
  • Since October 2025, Cognito uses a resource parameter to set the access token's audience (aud), on the Essentials tier and above, with managed login only. So the token names this server's URL.
  • Access tokens last an hour and refresh tokens 30 days, with refresh token rotation on. The MCP spec requires refresh token rotation for public clients.
  • Self sign-up is off. An administrator creates users.

2. Token checks and search

  • The server runs on AWS Lambda with the MCP Python SDK 2.3. AWS Lambda Web Adapter starts the app once per execution environment and hands it the requests that arrive at the function URL.
  • Every request's token is checked: the signature against Cognito's public keys, then the issuer, the expiry, that it is an access token, that our app client received it, that aud is this server's URL, and that it has the search scope. If anything doesn't match, the answer is 401 or 403.
  • After the check, the server calls the previous project's search Lambda with its own IAM role. That role can only call the search function and read the server's settings. The user's token is not passed on.
  • The tool name, description and result text are exactly the same as the local server's. Each result carries the page link, version and last-edited time, and a warning goes at the top when the sync has stopped.
  • There are no sessions. The 2026-07-28 spec removed them, and requests from older clients are also served without one. So any execution environment can take any request.
  • Three things are blocked for Lambda's sake. The change-notification stream is turned off, GET and DELETE get a 405 before they reach the SDK, and every response is a single JSON body. An open stream keeps its request from ever finishing; left alone, it keeps the function running, and billing, until it times out.

3. Logs

  • Every tool call and every refused request writes one JSON line to CloudWatch Logs: the user (Cognito sub), the client and its protocol version, the tool, the question's length, the number of results and warnings, the time taken (in total and for the search), and the server version (git commit and Lambda version). A refused request also gets the reason.
  • Tokens, emails and question text are never logged.
  • One Logs Insights query shows calls and average time per user, tool and server version.

4. Deploy and rollback

  • The function URL is attached to the Lambda's live alias, so the URL never changes.
  • A push to main makes GitHub Actions run the tests and deploy with CDK. A new Lambda version is published and the live alias moves to it. After the deploy, a check from outside confirms what can be seen without a token: the 401, the metadata, and the 405 for GET.
  • A rollback is a workflow run by hand with a version number. It moves only the alias to that version and runs the same check.
  • Both workflows use AWS roles assumed through GitHub OIDC. The deploy role may only assume the CDK bootstrap roles; the rollback role may only read and move the alias. Both trust only the main branch of this repository, matched by GitHub's numeric repository ID, so a repository re-created under the same name cannot use them.
  • The server version is the last commit that changed the server code, the infrastructure or the dependencies. A commit that only changes docs does not publish a new version.

Results

Measured on 26 October 2026 from a laptop in Sydney to the Sydney Region (ap-southeast-2). One user and one computer: these numbers show how each part behaves, not how a team would load it.

Sign-in

  • Claude Code (2.1.310) signed in and called the tool. It went through Cognito's managed login with the pre-registered client and the fixed callback port.
  • The token passed the aud check: Claude Code sent resource, and Cognito put the server URL into aud.
  • Cognito's discovery document has no PKCE entry (code_challenge_methods_supported), yet sign-in worked with no extra setting. The official MCP TypeScript SDK assumes S256 when that entry is missing.
  • The protocol version negotiated was 2026-07-28.
  • After Claude Code was closed and opened again, it did not ask to sign in again.

Response time

The same ten questions (questions 1 to 10 from the previous project's evaluation set) went to both servers, each after one warm-up call. Both servers call the same search Lambda.

Server Median Slowest
Local (stdio server on the laptop) 143.5 ms 159 ms
Remote (function URL) 170.5 ms 201 ms

The remote server's log shows that 130 ms of a 132 ms call was spent waiting for the search. Most of the difference is the extra network hop from the laptop to the remote server.

Cold starts

A new execution environment took 2.1 to 2.7 seconds to start (five Init Durations: 2,134, 2,679, 2,103, 2,600 and 2,712 ms). The first call to a newly deployed version took 3.1 seconds at the client.

Deploy and rollback

While GitHub Actions ran one deploy and two alias moves, the server version was asked every second: 272 answers, no errors.

Event From the start First answer after the alias moved Answers from the old version afterwards
Deploy a new version (push to main) About 90 s from the push (tests 35 s) 0.7 s 0
Roll back (version 4 → 3) 13 s from the workflow start 1.1 s 0
Roll forward (version 3 → 4) 11 s from the workflow start 1.2 s 0
  • "After the alias moved" means after CloudFormation finished updating the alias (deploy), or after the workflow moved the alias (rollback). The new version then answered 30 times in a row.
  • The new version answered before the deploy workflow logged that the deploy was done. The alias moves before CloudFormation finishes its cleanup.

Logs

One Logs Insights query showed calls and average time per user, tool and server version. For example, one user called search_team_docs 11 times on server version c912093.

Cost

Calculated with Sydney prices from the AWS Price List (as of 22 October 2026: $0.20 per million requests, $0.0000133334 per GB-second on arm64), before the free tier.

  • The whole measurement session: 298 Lambda invocations, 3.98 GB-seconds, $0.0001.
  • A warm tool call bills about 135 ms at 512 MB, mostly waiting for the search. 1,000 calls cost about $0.0011.
  • Each call writes about 0.6 KB of logs, under $0.001 per 1,000 calls.
  • The search Lambda's cost is the same with the local server, so it is not counted. The function URL itself has no extra charge.

Limits

  • Measured with one user on one computer. The deploy and the rollback were measured once each.
  • No rate limit. Requests without a token still start the function. This account's Lambda concurrency limit (10) acts as a cap, but a burst of requests could also hold back other functions in the same account.
  • The search does not know about permissions. Everyone who signs in sees the same documents, the same assumption as the previous project.
  • One user, created by hand. A company would connect its own identity provider to Cognito, or use it directly. Microsoft Entra ID doesn't support automatic client registration either, so the same pre-registration applies.
  • Cold starts take over 2 seconds. With regular use a warm environment answers, but the first call after a long idle period waits.

What the design missed

  1. The function URL renames the 401 header. The server's 401 carries a WWW-Authenticate header with the metadata URL and the scope. The Lambda function URL sends that header as x-amzn-Remapped-www-authenticate. The Lambda documentation doesn't mention it; AWS re:Post and the Serverless forum have reports of the same thing. The MCP spec asks the server for either the 401 header or the well-known URL, and asks clients to support both. Because the metadata was also at the well-known URL, sign-in still worked, and the scope was fixed in .mcp.json. The post-deploy check now reads the renamed header.
  2. With the local server still registered, the agent picks either one. I kept the local server for the comparison, so two tools had the same name. The same question was answered once by the remote server and once by the local one (confirmed in the remote server's log and the search Lambda's log). When moving from local to remote, remove the local registration.
  3. A Cognito resource server name cannot be a URL. To tie the token's scope and audience to this server, the resource server's identifier is the server URL. CDK uses the identifier as the name unless one is given, and names cannot contain : or /, so the first deploy failed. The name is now set separately, and a test checks the rule.

Next steps

  • Repository rules: Rule files such as AGENTS.md are read by the agent from the repository, so they cannot move to a remote server. Keeping rules consistent across repositories is the next post.
  • Rate limits and cost tracking: add per-user rate limits and usage records.
  • Company identity provider and permission-aware search: sign in with a company account, and search only the documents each person may see.
  • Agent check before deploy: start a new version on a different alias first, have an agent use the tool on a fixed set of questions, and move live only if it passes. A change to a remote server reaches everyone at once.

How it was built

The code, tests, CDK, workflows and measurement scripts were written with an AI coding agent (Claude Code). I made the decisions: going remote, the sign-in method, and what to measure and how.

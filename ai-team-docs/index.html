Up-to-date team docs for AI agents

A Confluence space is synced read-only every 10 minutes into a search index, and AI coding agents use it through one MCP tool. Every result carries the page link, version and last-edited time, and a warning appears when the sync stops.

The problem

As AI is used in more parts of software development, it more often needs to know the team's documents too.

  • Writing code: why the team decided things the way it did (decision records), and what to do when something breaks (runbooks)
  • Reviewing a pull request: whether the change follows the team's rules and decision records
  • Drafting a Jira ticket: whether a new requirement conflicts with existing documents

But this knowledge usually lives in a wiki, not in the repository. So wiki pages get copied into the repository or pasted into prompts. Those copies don't follow the wiki when it changes. The agent works from a stale copy, and nobody knows the copy is stale.

Why agents can't simply be handed the wiki

  • Copies go stale. When someone edits the wiki, the copy doesn't know, and nothing records when it was copied.
  • Access is broad. In some organizations, security or compliance rules keep AI coding agents from connecting to the internal wiki directly. Wiki and collaboration vendors are also adding admin controls that allow or block AI agent access.
  • Wiki pages are untrusted data. A page can contain text people can't see, or instructions aimed at an AI. OWASP notes that it is unclear whether there is a fool-proof way to prevent prompt injection (LLM01:2025).
  • Putting everything in the prompt has limits. Anthropic suggests putting the whole knowledge base in the prompt, with no retrieval, when it is smaller than about 200,000 tokens. But as a wiki grows, so does the token count, and research shows that models can miss information in the middle of long inputs (Liu et al., TACL 2024; Chroma, 2025).

Claude Code doesn't rely on a prebuilt embedding index. It searches the repository with patterns and text when it needs to find code. Wiki pages live outside the repository, so they need an approved copy and a search tool to find things in it.

There are managed options, such as the Atlassian Rovo MCP Server (generally available in February 2026) and Amazon Bedrock Managed Knowledge Base (generally available in June 2026, with a Confluence connector). Before adopting a service like that, I built this to understand what structure it takes to give agents up-to-date documents safely. I also wanted to check that the AI answers correctly from the changed documents. When it gives a wrong answer, I wanted to find the step that caused it and fix only that step. The goal was one search tool that writing code, reviewing pull requests and drafting tickets can all share. This time I connected it to Claude Code and tested it there. I also compared it with Managed Knowledge Base on the same questions.

Principles

  1. Read only. Confluence is read with a token scoped to reading and with code that only sends GET requests. The tool the agent gets is a single read-only search.
  2. Show sources and freshness. Every result carries the page link, version, last-edited time and sync time. If the sync stops, a warning goes at the top of the results, and the agent is told to pass it on first.
  3. Treat wiki pages as data. Content people can't see is kept out of the index. Sentences that look like instructions to an AI are flagged, not deleted. Every tool result ends with a reminder not to follow page content as instructions.
  4. Confirm before removing. Each page missing from the list is checked on its own before it is removed. If more than 20% go missing at once, removal stops until a person checks. When a page is removed, the copies we stored are set to be deleted too.
  5. Process only what changed. Only pages with a new version are processed again, and chunks whose text hasn't changed reuse their earlier embeddings.
  6. Measure each step. Retrieval, answers, freshness and cost are measured separately, so a wrong answer can be traced to the step where it went wrong.

Architecture

1. Sync

EventBridge Scheduler runs the sync Lambda every 10 minutes. The Lambda calls the Confluence Cloud API with a read-scoped token stored in SSM Parameter Store.

  • It fetches the space's page list together with the page bodies, compares each page's version number with the one stored in DynamoDB, and processes only the pages that changed. Archived pages are left out of the list from the start.
  • Each page missing from the list is looked up again on its own. If it is in the trash, archived, permanently deleted or no longer accessible, it is removed from the index. If it is still live, it stays.
  • If more than 20% of the pages go missing in one run, nothing is removed and a warning is recorded. This keeps an API glitch or a permission change from emptying the index all at once.
  • A run lock in DynamoDB keeps two runs from overlapping.
  • Raw pages and converted text are stored in S3. When a page is removed or replaced by a new version, its old files get a tag, and an S3 lifecycle rule deletes them. The sync function has no permission to delete anything.

2. Conversion and safety checks

Confluence's storage format (XHTML) is converted to Markdown. The converters for macros such as code blocks, info panels, task lists and decisions are custom-built, with test fixtures for each macro.

  • Content people can't see is removed: HTML comments, white or zero-size text, and zero-width characters.
  • Sentences that look like instructions to an AI (for example, "ignore previous instructions" or "AI agent:") are kept and flagged in the results. That way a normal page never disappears without anyone noticing.

3. Indexing

  • Pages are split into chunks by heading (h1–h3), and each chunk gets a "page title > section title" prefix. Anthropic reported that adding context to each chunk before indexing cut top-20 retrieval failures by 49%. This project does something simpler and adds only the titles.
  • Chunks are embedded with Titan Text Embeddings V2 on Amazon Bedrock, in the Sydney Region. A hash of each chunk's text is compared, so unchanged chunks reuse their earlier embeddings.
  • The keyword index (SQLite FTS5) and the vector file are bundled into one index and uploaded to S3. Then only the pointer to the current index changes.

4. Search

The search Lambda keeps a downloaded copy of the index and searches it two ways for each question.

  • Keyword search (BM25): page titles and section titles get extra weight. It covers exact names such as error codes and ticket numbers.
  • Semantic search: the question is embedded and compared with the chunks. It covers questions worded differently from the documents.
  • The two result lists are merged with RRF (Cormack et al., SIGIR 2009). At most two chunks come from any one page, and five chunks are returned.
  • There is no separate vector database. With a few hundred chunks, comparing all of them inside the Lambda is enough, and there is no fixed cost.

5. MCP tool

A local MCP server gives Claude Code one read-only tool, search_team_docs.

  • The MCP server runs with an IAM role that can only invoke the search Lambda. There is no public endpoint, and the agent side never holds the Confluence token.
  • Every result carries the page link, version, last-edited time and sync time. The last line shows when the index was last synced.
  • A warning appears at the top if the last sync was more than 30 minutes ago, the last run failed, removals were held back, or the token expires within two weeks.

Why this design

Decision Not chosen Reason
Fetch the page list every 10 minutes and compare versions Webhooks, CQL search Webhooks need an app or an automation rule on the Confluence side. CQL is only in the older API and works to the minute. The page list call returns every page's version
A read-scoped token and GET-only code The full permissions of a person's account Limits what the sync can do to reading
Hybrid search inside Lambda A vector database With a few hundred chunks, comparing them all is the simplest option and has no fixed cost. Every step can be explained and tested
Titan Text Embeddings V2 Other embedding models Runs within the Sydney Region, accepts inputs of up to 8,192 tokens, and is cheap
No reranker A reranking model No Bedrock reranking model can be called on its own in Sydney. Using another Region would send the documents outside Australia
Direct Lambda invocation, no public endpoint API Gateway A single-user setup doesn't need an endpoint to protect
Flag instructions only Delete instructions Keeps a normal page from silently disappearing

Results

I ran it on 30 Confluence pages for a fictional team that builds an inventory app: decision records, runbooks, team rules and reference pages. Claude wrote all of the documents and evaluation questions.

When the same author writes both the documents and the questions, they tend to share words, which favors keyword search. So I measured what share of each question's words also appear in its answer page. The first 26 questions averaged 57%, and five questions written to avoid the page's words averaged 29%. With 31 questions, small differences are within the margin of error (95% interval ±11–16 points), so read the results as trends.

Retrieval accuracy

I looked at the top 5 results for the 31 questions that the documents answer. hit@5 is the share of questions whose answer page is in the top 5. MRR is the mean of the reciprocal rank of the first right result.

Method All (hit@5 / MRR) 5 low-overlap questions
Keyword (BM25) 84% / 0.68 60% / 0.50
Semantic (Titan) 100% / 0.86 100% / 0.73
Hybrid (RRF) 100% / 0.89 100% / 0.74
Hybrid, no title prefix 97% / 0.82 80% / 0.70
Bedrock Managed Knowledge Base (defaults) 97% / 0.87 100% / 0.80
  • Keyword search alone missed questions asked in different words. On the low-overlap questions, it missed 2 of 5.
  • Adding the "page > section" prefix raised MRR from 0.82 to 0.89.
  • Managed Knowledge Base gave almost the same results with its defaults. The difference is one question.

Answer accuracy

The same model (Claude Haiku 4.5 on Amazon Bedrock, through the Australian inference profile) answered 34 questions, including 3 that the documents don't answer. Code checked whether each answer contained the facts it had to include (commands, numbers, names). I also read every answer and corrected the one case the code had scored wrong.

Prompt Top 5 search results All documents All documents + prompt cache
First 82% 68% 68%
After adding one sentence 85% (not run) 82%
  • The most common error was answering "not in the docs" when the answer was right there, especially when the model got all the documents. One sentence added to the prompt, "the docs usually contain the answer even when they use other words than the question", raised the all-documents method from 68% to 82%. One sentence in the prompt mattered more than the choice of method.
  • At this scale (30 pages, about 13,000 input tokens per question), giving the model all the documents with caching was about as accurate as search (82% vs 85%). For the 34 questions, search cost $0.08 and all documents with caching $0.09–0.13. Search used about 1,600 input tokens per question, one eighth as many.
  • So at this scale, the reason to use search is not accuracy. It is freshness, showing sources, and what happens as the wiki grows.

Freshness

This is how long it took, after a page was edited in Confluence, for the search tool to return the new version. Before each edit, the script waited a random 0–10 minutes, so edits landed at random points in the sync cycle.

10 edits at random times Median Max Min
Until searchable 6 min 49 s 9 min 32 s 1 min 18 s
  • Nearly all of that time is the wait for the next sync. Once a sync ran, the change was searchable within 3–19 seconds. An edit made right after a sync took up to 10 min 5 s. The 10-minute cycle sets the upper bound.
  • These 10 edits happened to fall early in the cycle, so the results are longer than the average for edits spread evenly across it (about 5 minutes, calculated).

Comparison: when a runbook changes

In the runbook "Roll back a bad deploy on dev", I replaced the fast path (re-running an earlier deploy with gh run rerun) with "don't re-run old deploys; use a revert PR only". Then I asked three agents the same question: "dev broke right after something got merged. What is the quickest way to get the previous working version running again?" The model (Claude Haiku 4.5) and the prompt were the same; only the documents differed.

  • Managed Knowledge Base kept giving the old command until its sync was run by hand. Its scheduled sync runs at most once a day. The manual sync took 151 seconds.

  • After the test, the page was put back the way it was.

When the sync stops

I turned the sync schedule off for 30 minutes. Once 30 minutes had passed since the last sync, the search tool put a warning at the top of its results: "WARNING: the last successful sync was 30 min ago (2026-10-20 09:52 UTC). Results may be out of date."

But the agent (Claude Haiku 4.5) didn't mention the warning in its answer, even when the tool description said that a warning at the top means the results may be out of date. When the instruction was changed to "When a result starts with WARNING, start your answer by telling the user what the warning says", the agent put the warning in the first line of its answer (tested once). Producing a warning was not enough; the agent had to be told explicitly to pass it on.

Comparison with Managed Knowledge Base

  • Accuracy: almost the same, as the table above shows. I created it with the default settings, and it took about five minutes from creation to the end of the first sync.
  • Token: the Knowledge Base's Confluence connector takes only the site URL. Atlassian accepts scoped tokens only at its gateway URL, so the read-scoped token was rejected at the site URL (401). Connecting with basic authentication therefore needed a token with all of the account's permissions. I didn't test the OAuth connection.
  • What results carry: the title, page URL and last-modified time. There is no version number, no sync time and no warning that the index has stopped updating. Every chunk I looked at was a single line of text, with no line breaks or code formatting.
  • Sync schedule: the schedule can only be daily, weekly or monthly. Syncing more often means calling the sync API yourself.
  • Cost: about $1.4 a month for the same usage (calculated from the price list). That is more than this search (about $0.12 a month), but both are small.

At this scale, the reason to build it yourself is not accuracy. It is the sync interval, the read-scoped token, the sources and warnings the agent gets, and being able to measure and fix each step.

Which step went wrong

Each step was measured on its own, and only the step with the problem was fixed.

Step What I found
Sync The default page list included archived pages. The sync now fetches current pages only.
Safety checks An ordinary sentence was flagged as an instruction to an AI. The check now catches only text that addresses an AI directly.
Chunking Without the title prefix, MRR dropped from 0.89 to 0.82.
Search For one question, search found the right page but not the section with the answer.
Answer Most wrong answers were not made up. They said "not in the docs" when the answer was there, and one sentence added to the prompt raised the all-documents method from 68% to 82%.
Answer For one question, search returned the right table, but the model still misread the log level of a 404. The error was in the answer step, not in search.

Managed Knowledge Base also returns its search results separately, so you can tell whether search or the answer was at fault. But the steps before that, conversion and chunking, could only be seen through the chunks that came out.

Limits

  • These results come from 30 fictional pages and 31 questions that Claude wrote. Small differences between methods are within the margin of error.
  • Search does not check each user's permissions. It assumes that only spaces everyone using the agent may see are synced.
  • The safety checks reduce the risk but can't remove it. Testing with attack pages is the next step.
  • There is no reranker.
  • The comparison test and the warning test were each run once.

What the design missed

  1. The measurement method decided the result. The first freshness measurement made the next edit as soon as the previous one showed up in search. But that moment is always right after a sync, so every edit waited out a full cycle, and only the worst case was measured (589–605 seconds). I changed the script to wait a random time before each edit and measured again.
  2. Copies of deleted pages stayed behind. Deleted pages dropped out of search, but their raw pages and converted text stayed in S3. A secret posted by mistake and then deleted would have stayed on our side. Now the files of deleted pages and old versions get a tag, and a lifecycle rule deletes them. The sync function still has no permission to delete.
  3. The warning was produced but not passed on. As described in "When the sync stops", the agent had to be told explicitly to pass the warning on.

Next steps

  • Connect pull request review: the earlier AI PR review project will use this search to find the team's decision records and rules as evidence.
  • Connect ticket drafting: when AI drafts a Jira ticket, it will use this search to find related documents and note in the ticket where the request conflicts with earlier decisions or procedures.
  • Test with attack pages: measure the safety checks with pages that contain hidden text and instructions aimed at an AI.
  • If several people use it: search that follows each user's permissions, and authentication, would be needed. Right now it is built for one person.

How it was built

The code, tests, CDK and evaluation scripts were written with an AI coding agent (Claude Code). Claude also wrote the sample documents and evaluation questions. I made the decisions: what to build, what permissions to grant, and what to measure and how.
